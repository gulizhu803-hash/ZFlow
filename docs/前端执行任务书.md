## 任务 A（P0）：把「执行流程」从手输 ID 改为下拉选择

```text
【Goal】
管理中心的「执行流程」页目前要求用户手工输入智能体 ID 才能查询，新增/编辑流程时 agentId、clientId 也全靠手打。
改为：agentId 与 clientId 都从后端字典下拉选择，选中 agent 后自动刷新该 agent 的流程列表。

【Boundary】
- 允许修改：frontend/app/pages/Admin.vue（主）；必要时 frontend/app/lib/admin-schema.json（仅当需要给字段加 options 提示）
- 不允许修改：其它任何文件

【后端契约（两个字典端点，均已在后端存在且可用）】
1) POST /admin/flow/client
   入参：无
   返回 data：Array<ClientDetailVO>，其中至少包含 clientId（客户端标识）、clientName（名称）
   用途：填充 clientId 下拉

2) POST /admin/agent/list
   入参(json)：{ keyword?: string, agentType?: string }（均可空）
   返回 data：Array<AgentVO>，其中至少包含 agentId、agentName、agentType
   用途：填充 agentId 下拉；支持传 keyword 做远程搜索（可选，若实现请做 300ms 防抖）

3) 现有已接的列表/增删改端点（保持原样，不要重写调用方式）：
   - 查列表：POST /admin/flow/agent，query: { agentId }  → data: Array<FlowVO>
   - 新增/编辑：POST /admin/flow/insert | /admin/flow/update，json: FlowManageDTO
   - 删除：POST /admin/flow/delete，query: { agentId, clientId }
   - 这些已由 Admin.vue 现有泛化逻辑（post("/admin/" + tab + "/" + ...)）覆盖，不要破坏该逻辑

【FlowManageDTO 字段（新增/编辑时必须满足）】
- agentId: string，必填
- clientId: string，必填
- clientRole: string，必填（执行角色标识）
- userPrompt: string，必填
- flowSeq: int，必填，>= 1
- originAgentId: string，可空；当用户修改了 agentId 时必须传"旧值"
- originClientId: string，可空；当用户修改了 clientId 时必须传"旧值"
说明：origin* 是"更新前定位字段"，用于后端定位旧记录。admin-schema.json 已声明这两个字段，
Admin.vue 现有 open()/save() 已实现从 target 回填 origin*，你必须复用，不要另写一套。

【Constraints】
- 字典按 tab 懒加载：只在首次进入 flow 页时拉取 /admin/flow/client 与 /admin/agent/list，不要放在应用启动时
- 两个字典请求失败时不能让整页崩：列表区显示错误提示，下拉降级为可手输（保留原手输能力作为兜底）
- 下拉必须可搜索（agent 多时手翻不现实）；用原生 <select> + 输入过滤或现有组件均可，不要引入新依赖
- 选中 agent 时通过现有的 post("/admin/flow/agent", { query: { agentId } }) 刷新列表；清空选中则列表清空
- 不要改动 resources 里 flow 的 id/columns 定义（keyQuery() 依赖 id: ["agentId","clientId"]）
- 未登录/demo 模式：Admin 页本身已由 allowed = userRole === "admin" 拦截，无需额外处理，但不要让它抛错

【Acceptance Criteria】
- [ ] 进入「执行流程」页，不输入任何 ID 即可从下拉选到 agent；选中后列表自动刷新为该 agent 的流程
- [ ] 新增流程：agent、client 从下拉选择，clientRole/userPrompt/flowSeq 正常填写，保存成功后列表出现该行
- [ ] 编辑流程并把 clientId 换成另一个 client：保存成功，且后端是"更新"而非"新增一条"（列表条数不变）
- [ ] 删除流程成功，列表刷新后该行消失
- [ ] 断开网络或后端返回错误时，页面显示错误提示，不白屏、不静默失败
- [ ] npm run build 通过（在 frontend 目录执行），退出码 0

【Required Evidence】
1. Admin.vue 的 git diff（完整）
2. 上述 6 条验收标准逐条自检结论
3. npm run build 的实际输出尾部 + 退出码
4. 如果你把 agent 下拉做成了远程搜索，说明防抖实现位置与触发条件
```

## 任务 B（P1）：广场「删除自己的发布」入口

```text
【Goal】
给「发现广场」加删除入口：用户只能删除自己发布的内容。该能力后端已有，前端从未做过（旧版也只导出未接 UI）。

【Boundary】
- 允许修改：frontend/app/pages/Plaza.vue；必要时 frontend/app/lib/workspace.js（仅当需要补状态更新函数）
- 不允许修改：其它任何文件

【后端契约】
POST /workspace/plaza/delete
  入参：query { plazaId: string }（必填，注意是 query 不是 body）
  返回：Result<Void>，成功即删除
  鉴权：普通登录用户即可；越权删除由后端拒绝

【Constraints】
- 归属判断：仅当该卡片属于当前用户时才渲染删除按钮（可复用 workspace.js 导出的 ownerId(auth) 与卡片上的 userName 比对）
- 二次确认：复用现有 Modal 组件，文案明确"删除后不可恢复"
- 删除成功后必须本地同步：从 items 移除该条、total 减 1；不要整页重新请求
- 失败走 report(e)，并且不要乐观删除（先等服务端成功再改本地状态）
- demo 模式（isDemo.value 为 true）下不发请求，只做本地移除，行为要与现有 demo 分支风格一致

【Acceptance Criteria】
- [ ] 自己发布的卡片可见「删除」，他人发布的卡片不可见
- [ ] 确认弹窗 → 确认后调用 POST /workspace/plaza/delete，列表与总数立即正确
- [ ] 取消弹窗不产生任何请求
- [ ] 构造他人 plazaId 的删除请求时，前端展示后端错误提示而非静默成功
- [ ] npm run build 通过

【Required Evidence】
1. Plaza.vue 的 git diff
2. 5 条验收标准逐条自检结论
3. 你如何判定卡片归属（贴出判断那一行代码）
4. npm run build 输出尾部 + 退出码
```

## 任务 C（P2）：用 /user/query/role 替换硬编码角色字典

```text
【Goal】
角色字典现在硬编码在 app/lib/demo.js 的 strategies 里，后端若新增 agentType 或改角色，前端不跟随。
改为：登录态下从 POST /user/query/role 拉取；未登录 demo 模式仍回落到 demo.js 的本地数据。

【Boundary】
- 允许修改：frontend/app/lib/workspace.js（主）、frontend/app/lib/demo.js（仅保留兜底，不要删除）
- 允许只读参考：AgentCard.vue / AgentShelf.vue / Agents.vue / Home.vue / Plaza.vue（会消费 strategies，尽量不改）
- 不允许修改：其它任何文件；不允许删除 demo.js 中的 strategies 兜底

【后端契约】
POST /user/query/role
  入参：无
  返回 data：Map<string, QueryRoleVO>，key 为 agentType，value 至少包含 roles: string[]
  鉴权：需要登录

【Constraints】
- 拉取时机：并入 workspace.js 现有启动/刷新流程（那个用 Promise.allSettled 的地方），不要新开一个独立生命周期
- 必须容错：该请求失败时不能让整页刷新失败（Promise.allSettled 的 rejected 分支要被处理），静默回落到 demo.js 数据并记录 loadError
- 消费方读取方式不变：对外仍暴露同名 strategies，避免改动 5 个消费组件
- demo 模式不发请求，直接用 demo.js 数据

【Acceptance Criteria】
- [ ] 登录后能在 Network 里看到 /user/query/role 请求，且页面角色分组来自接口数据
- [ ] 未登录 demo 模式页面照常显示角色分组（来自 demo.js）
- [ ] 人为让该接口 500，页面其它数据仍正常刷新，不整页报错
- [ ] npm run build 通过

【Required Evidence】
1. 改动文件的 git diff
2. 4 条验收标准逐条自检结论
3. 说明 strategies 的最终取值优先级（接口 / 兜底）与对应代码位置
4. npm run build 输出尾部 + 退出码
```
